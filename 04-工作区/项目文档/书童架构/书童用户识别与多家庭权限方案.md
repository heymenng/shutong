# 书童用户识别与多家庭权限方案

> 版本：V1.0  
> 日期：2026年6月27日  
> 问题：每个端口谁来用？书童怎么知道对方是谁？上云后怎么管理多个家庭？

---

## 一、当前问题

现在书童有三个主要端口：

| 端口 | 当前状态 | 问题 |
|---|---|---|
| 家庭端 `/` | 打开就能用，可选家长/孩子模式 | 不知道具体是谁，不知道是哪个家庭 |
| 师父端 `/master` | 默认以师父身份访问 | 没有严格身份校验 |
| 手机端 `/mobile` | 有密码登录，但只返回角色 | 不知道具体是哪个家长/哪个孩子 |
| OpenCode端 | 独立工具 | 与产品端完全隔离 |

核心问题：
1. **书童不知道"我是谁"**：每个请求只有 role（child/parent/master），没有具体身份；
2. **书童不知道"这是谁家"**：本地运行时默认一个家庭，上云后需要多家庭隔离；
3. **数据容易混淆**：多个孩子共用同一个对话历史，档案也可能串；
4. **权限边界模糊**：家长能看到什么？孩子能看到什么？师父能看到什么？没有明确规定。

---

## 二、核心思路

### 2.1 四元身份模型

书童要认识的，不是"端口"，而是"人"。

每个访问者，由四个维度确定：

```
家庭（Family） → 用户（User） → 角色（Role） → 当前陪伴对象（Child）
```

| 维度 | 说明 | 例子 |
|---|---|---|
| 家庭 Family | 一个家庭单位，上云后是独立租户 | 刘家、张家 |
| 用户 User | 家庭中的具体成员 | 爸爸、妈妈、嘟嘟、橙子 |
| 角色 Role | 该用户在系统中的权限身份 | 师父、家长、孩子、访客 |
| 陪伴对象 Child | 当前对话针对的孩子 | 和橙子说话时，child=橙子 |

### 2.2 关键原则

1. **先认人，再对话**
   - 任何有意义的对话之前，必须先确定用户是谁。
   - 不能确定时，只能进入"访客模式"或"注册流程"。

2. **家庭是数据隔离的最小单位**
   - 一个家庭的历史、档案、计划，对其他家庭不可见。
   - 师父角色可以跨家庭查看（用于管理和教学），但需要明确授权。

3. **角色决定权限，身份决定上下文**
   - 角色决定能看什么、能做什么；
   - 身份（具体是谁）决定加载哪个孩子的档案和历史。

4. **孩子以陪伴对象身份参与，但不具备管理权限**
   - 孩子只能看自己的东西、跟自己对话；
   - 不能看兄弟姐妹的隐私，不能改家长设置。

## 三、角色与权限设计

### 3.1 四种角色

| 角色 | 权限 | 适用对象 |
|---|---|---|
| **师父** | 全系统管理、训练书童、查看所有家庭档案、调整系统提示词 | 师父本人，或授权开发者 |
| **家长** | 管理自己家庭、查看/编辑孩子档案、查看家庭对话记录、设置陪伴偏好 | 爸爸、妈妈、监护人 |
| **孩子** | 与书童对话、查看自己的陪伴计划、记录自己的情绪/睡眠/运动 | 0-18岁被陪伴对象 |
| **访客** | 只能体验有限功能，不能保存数据 | 未登录用户、临时体验者 |

### 3.2 权限矩阵

| 功能 | 师父 | 家长 | 孩子 | 访客 |
|---|---|---|---|---|
| 与书童对话 | ✅ | ✅（在自己家庭中） | ✅（仅自己） | ⚠️ 限时体验 |
| 查看孩子档案 | ✅ 全部 | ✅ 自己家庭 | ✅ 仅自己 | ❌ |
| 编辑孩子档案 | ✅ 全部 | ✅ 自己家庭 | ⚠️ 部分自填 | ❌ |
| 查看对话历史 | ✅ 全部 | ✅ 自己家庭 | ✅ 仅自己 | ❌ |
| 设置系统提示词 | ✅ | ❌ | ❌ | ❌ |
| 管理家庭用户 | ✅ | ✅ 自己家庭 | ❌ | ❌ |
| 查看其他家庭 | ✅ | ❌ | ❌ | ❌ |
| 导出数据 | ✅ | ✅ 自己家庭 | ❌ | ❌ |

## 四、会话识别机制

### 4.1 登录后颁发的 Token 结构

用户登录后，后端颁发 JWT 或类似 token，包含：

```json
{
  "family_id": "family_xxx",
  "user_id": "user_xxx",
  "role": "parent",
  "child_id": "child_chengzhi",
  "exp": 1234567890
}
```

每次请求都带这个 token，书童就能知道：
- 这是哪个家庭；
- 这是家庭里的谁；
- 他是什么角色；
- 当前陪伴对象是谁。

### 4.2 端口与登录方式

| 端口 | 登录方式 | 说明 |
|---|---|---|
| 家庭端 `/` | 家庭通行证 + 选择身份 | 输入家庭密码后，选择"家长/孩子"，再选具体孩子 |
| 师父端 `/master` | 师父密钥 | 高强度密码，独立认证 |
| 手机端 `/mobile` | 家庭通行证 + 选择身份 | 同家庭端，界面适配手机 |
| OpenCode端 | 本地工具，不接入家庭系统 | 保持独立，只用于开发和测试 |

### 4.3 本地模式 vs 云上模式

**本地模式（当前）**：
- 默认只有一个家庭；
- 师父密码和家长密码可以相同或不同；
- 孩子档案存在本地 `04-工作区/档案区/孩子档案/`；
- token 也存本地 sessions。

**云上模式（未来）**：
- 每个家庭有独立的 family_id；
- 用户需要注册/登录；
- 数据存在云端数据库；
- 支持多设备同时在线；
- 支持一个家庭多个家长、多个孩子。

## 五、数据隔离方案

### 5.1 本地阶段

即使本地，也应该按家庭隔离：

```
03-引擎区/书童程序/数据/
  ├── 家庭/
  │   └── default_family/
  │       ├── 用户/
  │       ├── 孩子档案/
  │       ├── 对话历史/
  │       ├── 陪伴计划/
  │       └── 设置/
```

当前只有 `default_family`，但结构要为未来扩展预留。

### 5.2 云上阶段

云端数据库
  ├── families

## 六、端口身份认定流程

### 6.1 首次使用流程

1. 打开家庭端/手机端
2. 如果是首次，进入"创建家庭"流程：
   - 设置家庭名称；
   - 设置家庭通行证；
   - 添加家长；
   - 添加孩子（姓名、年龄、性别、发育阶段）。
3. 创建完成后，颁发家庭 token。

### 6.2 日常使用流程

1. 打开端口；
2. 输入家庭通行证；
3. 选择"我是谁"（爸爸/妈妈/嘟嘟/橙子）；
4. 如果是家长，选择"今天要陪伴谁"；
5. 进入对话。

### 6.3 师父端流程

1. 打开 `/master`；
2. 输入师父密钥；
3. 选择要查看/管理的家庭；
4. 进入师父控制台。

## 七、对当前代码的修改建议

### 7.1 立即可以做

1. **扩展 session 结构**
   - 当前：`{role, child_id, created_at}`
   - 改为：`{family_id, user_id, role, child_id, created_at}`

2. **家庭端/手机端登录时选择具体身份**
   - 输入家庭密码后，列出家庭中的用户；
   - 用户选择"我是爸爸"或"我是橙子"；
   - token 中写入 user_id 和 child_id。

3. **默认创建一个本地家庭**
   - 本地运行时，自动创建 `default_family`；
   - 把现有的嘟嘟、橙子档案归到这个家庭下。

4. **根据 user_id 加载上下文**
   - `/api/chat` 时，用 token 中的 child_id 加载对应档案和历史；
   - 家长说话时，可以明确说"我今天想和嘟嘟聊"。

### 7.2 后续上云时做

1. 用户注册/登录系统；
2. 云端数据库迁移；
3. 多家庭数据隔离；
4. 家长授权管理；
5. 设备绑定和在线状态。

## 八、书童的自我定位

不管端口怎么变，书童的定位不变：

> **我是每个家庭的伴读书童，不是替代父母，而是陪伴每个孩子。**

所以用户识别不是为了监控，而是为了：
1. **提供对的上下文**：对嘟嘟和对橙子，说的话不一样；
2. **保护隐私**：兄弟姐妹之间不串数据；
3. **支持家长**：让家长看见孩子的成长，但不替家长做决定；
4. **尊重边界**：孩子和孩子之间、家庭和家庭之间，数据不混用。

---

## 九、总结

师父问的问题，本质是：**书童怎么知道对面是谁？**

答案：

> **用"家庭-用户-角色-陪伴对象"四元模型识别，用 token 传递身份，用权限矩阵控制边界。**

现在本地阶段先建立结构，未来上云时自然扩展。

这样书童就不会 confusion：
- 在家庭端，知道这是刘家的爸爸在跟橙子说话；
- 在师父端，知道这是师父在查看某个家庭的档案；
- 上云后，知道张家和李家是隔离的，数据不串门。

这就是书童的用户识别方案。
